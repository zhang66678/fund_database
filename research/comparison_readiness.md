# 基金对比开发前的数据检查

检查日期: 2026-10-14.

检查对象: 本地 `data/fund_database.duckdb` 中已有净值的 5 只基金. 通过 Repository 和 FundService 只读查询, 未请求 Tushare, 未修改数据库或指标公式.

## 结论

现有 4 只混合型基金已经足够验证两只及多只基金对比, 本步骤无需增加基金数量.

- 第一轮使用 `000001.OF` 华夏成长和 `040001.OF` 华安创新, 验证共同区间和累计收益曲线.
- 随后加入 `005827.OF` 和 `009653.OF`, 验证三只及四只基金的日期对齐.
- 第一轮验证区间为 `2025-10-13` 至 `2026-10-13`. 四只基金均有 243 条开市日复权净值, 现有七项指标均可计算.
- 更长的已验证共同连续区间为 `2020-12-11` 至 `2026-10-13`, 四只基金各有 1412 条开市日复权净值, 七项指标同样可计算.
- `028361.OF` 暂不作为第一轮日频指标对比样本. 它仍保留在数据库, 以后应根据实际披露情况判断适用性.

以上结论是按当前程序的 SSE 日历及日频指标口径进行的输入检查, 不代表已经通过外部资料核实所有基金的数据完整性或实际适用日历. 候选窗口用于开发验证, 不是自动修改用户查询区间的规则.

## 全历史区间的限制

本地 SSE 日历覆盖 `2001-12-18` 至 `2026-10-14`, 共 9067 个自然日, 无重复日期或非法开闭市标记. 日历末日不等于最新净值日期.

| 代码 | 已知 SSE 开市日未找到净值的日期数 | 未被日历覆盖的自然日数 | 现有全历史指标结果 |
| --- | ---: | ---: | --- |
| 000001.OF | 20 | 0 | 开市日净值不连续, 不可计算 |
| 005827.OF | 25 | 0 | 开市日净值不连续, 不可计算 |
| 009653.OF | 13 | 0 | 开市日净值不连续, 不可计算 |
| 028361.OF | 6 | 0 | 开市日净值不连续, 不可计算 |
| 040001.OF | 0 | 88 | 日历未覆盖最早一段, 不可计算 |

华安创新的 88 个自然日为 `2001-09-21` 至 `2001-12-17`. 这一段的开市日数量不能用当前日历判断, 表中的 0 只针对已覆盖部分, 不能理解为全历史没有缺口.

缺少 SSE 开市日记录不直接证明 Tushare 抓取失败. 还需区分基金实际披露频率, 适用日历和来源缺漏; 本次没有填充, 插值, 删除或重新下载这些记录.

### 缺口定位

- `000001.OF`: 20 个日期位于 `2001-12-19` 至 `2002-01-29`, 集中在成立初期.
- `005827.OF`: 25 个日期不仅出现在成立初期, 还分布于 2018 年底及 2019 年, 最后一个为 `2019-07-31`. 应单独核对其实际交易和披露日历.
- `009653.OF`: 13 个日期位于 `2020-11-19` 至 `2020-12-10`, 集中在成立初期.
- `028361.OF`: 当前仅有 `2026-09-18`, `2026-09-24`, `2026-09-30`, `2026-10-09` 四个净值日期. 其首末日之间的 10 个 SSE 开市日中, 6 个未找到净值. 暂不能直接套用现有连续日频模型.

四只混合型基金按最早和最晚记录取交集, 得到 `2020-11-18` 至 `2026-10-13`. 这个区间内部仍包含大成丰享回报的 13 个缺口. 因而仅取各基金日期边界的交集, 并不能保证整个区间适合计算日频指标.

| 区间 | 基金代码 | 各基金实际计算起止日相同 | 每只开市日净值数 | 七项指标 |
| --- | --- | --- | ---: | --- |

两个区间各 4 只基金, 共 8 组候选输入均通过当前计算入口. 不同起始日得到的指标不可混作同一区间的对比结果.

## 对比功能的实现边界

1. 服务层接收基金代码列表及查询区间, 返回共同区间和逐只基金结果. 第一轮用两只验证, 数据结构同时支持多只.
2. 累计收益由复权净值计算, 使用相同基期, 不修改存储中的三种原始净值.
3. 七项指标继续复用现有方法. 跨越不连续区间时明确报告不可计算, 不通过填补或删掉开市日缺口生成连续收益.
4. 页面明确显示实际比较区间. 不能为了让某只基金通过检查而悄悄调整其起始日.
5. 先完成服务层的两只基金验证, 再接入前端对比页面.

此报告只反映本次本地数据状态, 后续更新数据库后需要重新检查相应区间.

## 服务层实现与验证

已在 `services/fund_service.py` 增加 `FundService.get_comparison(ts_codes, start_date=None, end_date=None)`. 不依赖页面, 不调用 Tushare, 不修改数据库.

- 支持两只及以上基金, 代码规范化后去重, 保留选择顺序.
- 先按用户区间查询, 再取各基金净值覆盖范围的交集. 实际起止日为该范围内首末 SSE 开市日; 两个边界必须都有各基金的有效正复权净值, 否则提示调整区间.
- 使用完整的 SSE 开市日索引对齐, 中间缺失或无效值在派生曲线中保留为 NaN, 不前向填充, 不插值.
- 累计收益为 `adj_nav(t) / adj_nav(共同起点) - 1`, 以小数返回, 每只基金从 0 开始. 非开市日披露不进入对比曲线, 与当前指标的日历口径保持一致.
- 逐只调用现有 `get_metrics`, 保留七项指标及其区间, 样本数, 年化参数等说明. 某只基金不可计算时, 记录原因, 不影响其余基金或已知日期的累计收益.
- 无共同区间, 缺少某只基金的数据, 日历覆盖不足或边界净值无效时, 明确抛出 ValueError. 不自动绕开内部缺口.

返回结构:

| 字段 | 含义 |
| --- | --- |
| requested_start_date / requested_end_date | 用户请求的 ISO 日期字符串, 未指定时为 None |
| start_date / end_date | 实际共同计算区间, ISO 日期字符串 |
| funds | 规范化后的基金代码与名称映射 |
| cumulative_returns | DataFrame, 第一列 nav_date, 其余列为各基金代码, 数值为小数收益率 |
| metrics | 各基金原有 get_metrics 完整结果, 不可计算时为 None |
| errors | 不可计算指标的基金代码与具体原因 |

可在项目根目录的 Python 交互环境调用:

```python
from datetime import date
from database.duckdb_repository import DuckDBFundRepository
from services.fund_service import FundService

service = FundService(DuckDBFundRepository())
result = service.get_comparison(
    ["000001", "040001"], date(2025, 10, 13), date(2026, 10, 13),
)
print(result["start_date"], result["end_date"])
print(result["cumulative_returns"].head())
print(result["metrics"])
```
